# Full backup/restore via SQLcl Data Pump (production-grade path)

This is the more robust alternative to the manual per-table INSERT process
used earlier for master/security data — it captures **everything**
(structure, all data, BLOBs/CLOBs included) directly from Oracle's metadata
dictionary via Data Pump, rather than a re-generated DDL/DML script. This is
the method intended for the actual production cutover.

## Prerequisites

- SQLcl installed locally (23.x+ recommended — check with `sql -version`)
- Wallet downloaded for the OLD (source) database
- Wallet downloaded for the target database (once provisioned)

## 1. Export from the OLD (source) database

```
sql /nolog
SQLcl> set cloudconfig /path/to/old_wallet.zip
SQLcl> connect <schema_user>/<password>@<old_db>_high

SQLcl> datapump export full_bkp schemas=<YOUR_SCHEMA_NAME> file=full_bkp.dmp
```

Produces `full_bkp.dmp` on your local machine. This captures the OLD
database's schema **as it currently is** — it does **not** include the
surrogate-PK fix or the `apex_auth_fn` fix, since those were only applied to
the dev instance/repo, never to the live OLD database.

## 2. Provision a fresh target instance

Same as before: OCI Console → Create Autonomous Database → workload type
**Transaction Processing**, Always Free.

## 3. Import into the fresh instance

```
sql /nolog
SQLcl> set cloudconfig /path/to/new_wallet.zip
SQLcl> connect <schema_user>/<password>@<new_db>_high

SQLcl> datapump import full_bkp file=full_bkp.dmp
```

## 4. Post-import fixes (in order)

1. **`scripts/data_migration_00_alter_pk_on_populated_tables.sql`** — adds
   the surrogate ID + IDENTITY column to the same 18 tables as before, but
   via `ALTER TABLE ADD` instead of `CREATE TABLE`, since these tables now
   already have data from the import. `ADD ... GENERATED BY DEFAULT AS
   IDENTITY` on a populated table auto-backfills sequential values for
   existing rows (supported since Oracle 12c) — **no separate identity
   resync needed after this**, unlike the manual-INSERT path.
2. **`scripts/data_migration_04_post_import_fixes.sql`** — grant
   `DBMS_CRYPTO` (as ADMIN) and fix the `apex_auth_fn` schema qualifier
   (same two issues hit on the manual dev migration).
3. Configure the APEX workspace and import the app export, same as
   `docs/new-instance-setup.md` describes.

## 5. Verify

- Login (exercises `apex_auth_fn` → `sec_auth_pkg` → `DBMS_CRYPTO`)
- Row counts on a few tables per module, spot-check against the source
- SIM assignment and bike assignment flows specifically

## Why this is better for the real production cutover

- No manual per-table export/import — one export, one import
- No duplicate-statement/redundant-index artifacts (those came from the
  DDL-generation wizard, not from Data Pump's dictionary-based capture)
- BLOB/CLOB columns (employee photos, document scans, audit log) transfer
  correctly and automatically — the manual INSERT-statement method couldn't
  handle these at all
- Identity/sequence state is preserved automatically for columns that
  already had IDENTITY before export

## What's still manual

The 18-table surrogate-PK fix and the `apex_auth_fn` qualifier fix aren't
part of the OLD database yet, so they're re-applied after every fresh
import via steps 4.1–4.2. If this becomes a recurring rehearsal, it's worth
applying both fixes directly to the OLD database once (turning it into the
clean baseline) so future exports carry them automatically — hold off on
that until you're ready to make that call, since it modifies the live
source system.
